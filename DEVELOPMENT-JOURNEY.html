Date: 2026-10-01
Deliverable: this document, DEVELOPMENT-JOURNEY.html, in dot_vs_swarm_ethan\
Brief: "jev use cases that have not been widely discussed" (first run, argument to /swarm-brainstorm)
Model: Sonnet 5.5 (claude-sonnet-5-5) as the parent session. Subagents used the Agent tool with subagent_type: general-purpose and no model override.
Source of this text: the live session transcript and the 14 subagent completion notices. Nothing here is reconstructed from memory of an earlier session.

See also: the brainstorm results, which list every candidate and the two chosen ideas.

The short version. /swarm-brainstorm contains no code and no agent definitions. It is one prompt with three parts: a goal, a search strategy ("as many different angles as possible"), and three evaluation views. The prompt ends with one permission: "You may delegate. Organize the work as you think is best."

In this session the parent model read that permission and chose the structure. It ran the prompt twice, on two different evidence bases. Each run used 7 subagents in two stages. A third stage had no subagents: the parent merged the reports and judged them. The rest of this page shows what happened, stage by stage.

1. The brief: what was actually being asked

The session began after /clear. The user typed /swarm-brainstorm with the argument "jev use cases that have not been widely discussed". The skill text then loaded into the context. Its procedure has four steps: take the topic, run the prompt with {TOPIC} replaced, start subagents as judged useful, and report four things (the chosen idea, the reason, the ranked rejected list, and the number of subagents started).

The skill's source is Ethan Mollick, "The Dot and the Swarm". Its rule: do not define teams, roles, or agent counts. Mollick's own prompt made a model start 3 agents with no team sketch. The skill was written in an earlier session. HANDOFF.md records that it was created, never run, and that its four planned tests were still to do.

Interpretation, and an ambiguity left open

I could not read "jev". The folder gave no clue. A grep for \bjev\b|JEV matched only two minified asset files of the saved article (1580.d88a54d8.css and 1580.c49ad9e4.js.download). I asked the user for the full name and started no agent. This cost one turn. The user answered with a second invocation: "jev use cases that have not been widely discussed. do search/research on jev". That is the brief the agents worked from.

Later the user changed the evidence base: "forget your earlier research results. use these instead", followed by two URLs, the TypeSafe AI launch blog and the yibie/awesome-jev list. I treat this as a second run of the same skill. I kept the first run in this document because it shows how the same prompt produced a different structure on different evidence.

Invisible constraints on this session

  • ~/.claude/CLAUDE.md: ASD-STE100 sentences, precise (non-rhetorical) claims, plain-language explanation, and the "finish, or say what you left" rule.
  • The ponytail mode (level full) and focus mode. Focus mode means the user saw only my final message of each turn. Each final message therefore had to carry the findings by itself.
  • Two skills: swarm-brainstorm and, for this document, dev-journey.

There was no environment to repair. The work needed only the Agent tool, WebSearch, WebFetch, Bash, Grep, Glob, and Read. Two items were reused from earlier sessions: the skill file ~\.claude\skills\swarm-brainstorm\SKILL.md, and HANDOFF.md, which told me the skill's purpose, its source, and its untested status.

Identifying the topic (run 1, stage 0, no agents)

After the user said to research it, I loaded WebSearch and WebFetch with ToolSearch and ran three searches in parallel: "JEV AI agents use cases", "jev" claude code OR LLM OR agent OR tool 2026, and "JEV Japanese encephalitis virus new applications 2026". The first two returned the same entity. The third returned virology papers, so I dropped it. Result: Jev is the "System One" decision model from TypeSafe AI. It returns a typed answer with probabilities instead of text. Search results gave 15 Sep 2026 as the launch date. A later agent found a page that says 28 Sep, and I left that unresolved.

What the two runs show. The same prompt produced the same overall shape twice: a stage that gathers and maps, a stage that ideates from separate angles, and a judgment step in the parent. Both runs used 7 agents. The split differed: 3 then 4 in run 1, and 4 then 3 in run 2. The data does not show why. Two runs on one task cannot support a claim that the model scales the agent count to the task size. HANDOFF.md lists that as an open test, and this session did not close it.

Why the "angles" matter

The skill's search strategy says only "as many different angles as possible". The parent turned each angle into a separate briefing, so the ideators did not repeat one another. In run 1 the briefs shared a "do not propose" list built from the coverage agent's saturated categories. Without the stage before, that list could not exist. This is where the staging changed the content of the ideas.

Run 1, stage 1: orient (3 agents)

Agent 1.1: Facts and limits

Call label: Jev facts and limits · 31 tool uses · 113,672 tokens · 286 s

Why this agent. Every later agent needed correct facts about Jev. The search snippets and the listicles disagree with each other on basic numbers. I gave one agent the job of reading only primary sources (the vendor site, the docs, the API reference) and of sorting every claim into "verified" or "not verified".

What the prompt does. It names the entity and repeats the numbers I had from search snippets ("p50 about 230 ms"), without a source. It lists the topics to cover. It names two secondary sources to test, one of which claims a pitfall the vendor omits. It fixes the output at three numbered parts and 700 words. The third part asks for use cases that the listicles miss, so this agent also did a small amount of ideation.

What came back. Three question types (noul, choice, score). Price $0.042 per million input tokens. A 64k token limit for the state plus all questions and a 32k limit for the state plus the longest single question. 255 options for choice. Rate limits of 100K tokens per second and 40 requests per second. Nine documented failure modes for jev-1.13, including counting, math, and date comparison. A reranking result on legal retrieval (top-1 from 5% to 18%, top-10 from 38% to 62%, 1,200 calls for $0.0645). A batching result: 13 questions in one request were 12.2 times cheaper and 10.0 times faster. It listed unverified claims: the gist's error rates for positional references (86 of 320 wrong at 150 items per request), and the "p50 about 230 ms" figure, which has only a community plugin as its source. The vendor gives a range of 70 ms to 500 ms.

Limits. The agent had no API key, so it made no call and worked from documentation only. The agent also reported that a listicle (the Flavio Copes post) quotes rate limits that differ from the vendor page.

How I used it. The 40 requests-per-second limit changed the cost estimate of the run-1 winner. Token cost alone gave about 1.1 hours at 100K tokens per second. The request limit gave about 6.9 hours. The failure list (counting, math, dates) is the reason the winning design gives numbers and dates to code. The agent's 64k and 32k split reached the user in my report, but the four ideators had already received only the 32k figure in their briefs.

What the 14 prompts have in common

Every prompt has the same parts, in nearly the same order.

  1. Context. What Jev is, with the numbers that matter. Run 1 gives search-snippet numbers. Run 2 gives the blog's numbers.
  2. Known limits. The failure reports from earlier agents or from the list.
  3. A "do not propose" list. The saturated categories found by the coverage work. Ideators in run 1 get two such lists (widely discussed, and already built but niche).
  4. One angle. The only part that differs in a large way between agents of the same stage.
  5. The task and the output shape. A fixed list of what to report for each candidate, and a word cap of 700 or 800.
  6. An evidence rule. "Do not invent facts or URLs", or "Quote entry text exactly".

The two runs differ in how the novelty check works. In run 1 each ideator searches the web. In run 2 web search is off, and each ideator greps the local copy of the list with at least three keywords per candidate. The skill's third evaluation view ("what other publications are covering") is therefore a web search in run 1 and a grep in run 2.

7. How I chose the agents and the number

Short answer. The numbers 3, 4, 4, and 3 were judgments that I made while writing the tool calls, and I have no record of a calculation. 7.1 What the skill decided and what I decided

The skill states no count, no team, and no role. It ends with "You may delegate. Organize the work as you think is best", and its procedure says "Decide yourself how many subagents to start". 7.3 Run 1: how the 3 and the 4 came about

  1. Whether to delegate. I searched first, in the parent, only to learn what "jev" meant. Once I knew, I chose to delegate, because the work needed many pages read and several points of view. The alternative was to read everything in one context.
  2. Three agents in stage 1. I named three questions that need different sources: what Jev is (primary sources), what has been written about use cases (articles), and what people built (repositories and threads). I could not name a fourth distinct question. I did not use one agent, because one agent would mix primary and secondary sources and would have to count 20 or more pages.   3. Four agents in stage 2. I chose four angles that did not overlap each other or the saturated list. The angles came from four sources: the zero-coverage domains of agent 1.2 (domains), my own reading of the product description (Jev as a component), the wording of your topic (personal and civic uses are less discussed), and the failure reports of agent 1.3 (probability as product).   4. The reader view stayed in the parent. I judged this view myself. I wrote down no reason at the time. My untested reconstruction is that a reader view needs the finished candidates, and that a ranking needs all reports at once.
  5. Cost. Each agent used 80,000 to 115,000 tokens. I set no budget and made no cost comparison. Run 1 used 686,676 subagent tokens.

7.4 Run 2: how the 4 and the 3 came about

Reasons that I can offer now, both untested: one agent per file would repeat the prompt overhead 16 times, and two agents would each read 80 KB or more, which risks skimming.

9. What went wrong, and the fixes

  1. The topic was unreadable. "jev" matched nothing useful in the folder. I asked in plain text instead of guessing, and started no agent, because a wrong topic would have been copied into every subagent brief.
  2. The search that returned the wrong entity. The query "JEV Japanese encephalitis virus new applications 2026" returned virology papers. The other two queries agreed with each other, so I dropped it.
  3. WebFetch failed on the GitHub list. The tool's answer: "I cannot provide the complete structure you've requested because the web page content provided does not contain the actual list contents." Fix: curl to the GitHub tree API, which showed README.md (231,420 bytes) and 16 files under categories/, then curl of each raw file into the scratchpad.
  4. My brief had four errors, and the agents caught them.
    • Run 1: I gave the ideators a 32,000-token context limit. The facts agent found 64k for the state plus all questions and 32k for the state plus the longest question.
    • Run 2: I wrote that scientific-pipelines had 1 entry and compliance-legal had 3. The map agent found 0 and 2. The extra count was the template line inside a code block.
    • Run 2: I wrote that the list had no LangGraph entry. An ideator found typesafe-jev-workflow.
    I gave the agents the sources themselves, which is why they could check my summary of those sources.
  5. I misstated the list size. I said "about 480 entries". The four mappers' tallies sum to 552 (156 + 115 + 142 + 139), and a line count of - lines across the category files gave 568, which includes template lines. The tallies are hand counts and can be off by 1 or 2 per category.

  8. Hook notices. A "Coach" hook asked me to surface two notes verbatim. The first said the prompt was over 8k characters, which did not match the user's short message. The second said the session had reached about 156k context tokens. I surfaced both.
